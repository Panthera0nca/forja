# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

**DataForge** is a CLI tool (`dfg` / `dataforge`) that scaffolds and operates data engineering projects with a strict layered architecture (Sources → DTOs → Transforms → Repositories → Services → Pipelines). It is **not** a data project itself — it is the generator/operator of such projects.

The repo has two distinct parts:
- `src/dataforge/` — the CLI tool itself
- `miproyecto/` — a sample project generated by `dfg init miproyecto`, used for reference/testing

## Setup and install

```bash
pip install -e .           # installs as `dataforge` and `dfg`
pip install -e ".[dev]"    # includes pytest + ruff
```

## Common commands

```bash
# CLI development
dfg init <name>            # scaffold a new ETL project
dfg status                 # detect project from cwd (walks up for dataforge.toml)
dfg add entity <name>      # generate DTO + repository + SQL migration

# Testing
pytest -v                  # run all tests
pytest tests/test_foo.py::test_bar  # run a single test

# Linting / formatting
ruff check src tests
ruff format src tests
```

Tests that touch Postgres are skipped automatically unless `DATABASE_URL` is set. For DB tests, start Postgres first:

```bash
# from within a generated project directory (e.g. miproyecto/)
docker compose up -d
```

## Architecture of the CLI (`src/dataforge/`)

### Command → core flow

`main.py` registers all commands on a Typer app. Each command lives in `commands/<name>_cmd.py`. Commands delegate to two core modules:

- **`core/project.py`** — detects whether the cwd is inside a DataForge project by walking up the tree looking for `dataforge.toml`, then parses it via `ProjectManifest`
- **`core/templates.py`** — renders Jinja2 templates from `src/dataforge/templates/` into the destination directory
- **`core/config.py`** — two-level config: `~/.config/dataforge/config.json` (global) and `dataforge.toml` (per-project manifest)
- **`core/ui.py`** — all Rich output goes through `UI`; never use `print()` directly in commands

### Template system

Templates live under `src/dataforge/templates/` in two groups:
- `etl_project/` — full project scaffold (used by `dfg init`)
- `components/entity/` — per-entity files (DTO + repository + migration, used by `dfg add entity`)

Template conventions:
- Files ending in `.j2` are rendered with Jinja2 (suffix is stripped at destination)
- Directory/file names containing `{{package_name}}` are interpolated before creation
- Files named `_dotfile_X` become `.X` at the destination (avoids packaging issues with dotfiles)

### Generated project architecture (`miproyecto/` shows the pattern)

```
src/<package>/
  sources/     # Protocol: fetch() → Iterable[raw]  (no validation, no persistence)
  dtos/        # Pydantic models — contracts between layers
  transforms/  # Pure functions: clean, normalize, validate
  repositories/ # BaseRepository subclasses: raw SQL via psycopg3 dict_row
  services/    # Orchestration: fetch → transform → repository.save
  pipelines/   # Runnable ETL jobs
  db/connection.py  # psycopg3 connection pool
```

`BaseRepository` (in the generated `repositories/base.py`) provides `execute`, `execute_many`, `fetch_one`, `fetch_all` — all using parameterized SQL (`%s`), never f-strings with values.

`Source` is a `Protocol`, not a base class — any object with `name: str` and `fetch() -> Iterable[T]` satisfies it.

### Adding a new command

1. Create `src/dataforge/commands/<name>_cmd.py`
2. Register it in `main.py` via `app.command(name=...)` or `app.add_typer(...)`
3. Commands that operate on a project must call `detect_project()` first and exit early if `None`

### Adding a new component type (beyond `entity`)

1. Add Jinja2 templates under `src/dataforge/templates/components/<type>/`
2. Add a subcommand under `add_cmd.py` following the `add_entity` pattern
3. Use `render_file(template_rel_path, destination, context)` for per-file generation

## Key design principles

- **No ORM** — repositories write raw SQL; queries must be visible and debuggable
- **Additive only** — `dfg add <thing>` never touches existing files, only creates new ones
- **No global state** — all config comes from `dataforge.toml` in the project root
- **Stubs are intentional** — commands like `fetch`, `run`, `inspect`, `migrate` exist to define the CLI surface; implement them in order of real usage need
